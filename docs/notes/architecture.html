Single-Cell IDS — how the code handles size

Data comes in as cells × genes. IDS expands each gene into 6 feature-columns, correlates every feature pair, then squashes it back to one score per gene pair (a genes × genes table). Two things can get too big.

The problem · two ways it blows up

grows with CELLS

The expanded data grid

cells × (6·genes). 27M cells makes this astronomically tall. Linear in the number of cells.

grows with GENES²

The correlation table

(6·genes) × (6·genes). 20k genes → ~120k×120k ≈ 14 billion numbers. Quadratic in genes.

The pipeline · in words

1

Load the data

A .h5ad, a .csv, or a 10x folder — the --prefix flag is for GEO datasets like GSE194315 whose files are named PBMC-01-1.matrix.mtx.gz. Result: a cells × genes grid, usually stored sparse (mostly zeros, so only the non-zeros are kept — that's how single-cell data avoids being enormous on disk).

2

Preprocess  preprocess()

Normalize each cell for its sequencing depth, optionally pick the most variable genes, and scale each gene into the [0, 8] range the feature map expects. It stays sparse here if you're using a batched path.

3

Choose how to compute

This is where the two tricks live. Three routes, all returning the same d × d IDS table:

  • No flags → hand the whole grid to compute_IDS in one shot (fine for small data).
  • --block-size N → Trick 1, gene-batching, via ids_batched.py.
  • --cell-batch N → Trick 2 + Trick 1 together, via ids_streaming.py (for when there are too many cells).
4

Extract modules  extract_modules()

Take the finished IDS table, keep only the strong gene-pair links, and find clusters of genes that are all interlinked — those clusters are your co-expression modules.

Step 3 · three paths, one identical answer

DIRECT

Call the engine once

Use when: data fits in RAM

Hand the whole matrix to the authors' compute_IDS. Fastest, most precise, uses their GPU path.

→ ids/ (their code, unchanged)
TRICK 1

Batch over GENES

Use when: many genes, cells fit

Do a small block of genes at a time; stitch blocks into the full table. Tames the genes² explosion. Densifies one block at a time → also how sparse is handled.

→ ids_batched.py
TRICK 2

Batch genes + stream CELLS

Use when: too many cells for RAM

Also feed cells in slabs, in two passes (mean pass, then centered correlate pass — the paper's order). Tames both explosions. Plain NumPy, no p-values.

→ ids_streaming.py

Inside the two tricks

Trick 1 — gene blocks (ids_batched.py)

genes split into blocks → compute_IDS(block i) compute_IDS(block i, block j) → tile into full table

Each small block is one call to their engine. Peak cost is one block's table, not the whole 120k×120k.

one block at a time → full table

Trick 2 — two passes over cell slabs (ids_streaming.py)

Pass 1
slabs → means
(save to disk) → Pass 2
slabs → subtract means
→ centered correlation → reduce → IDS

Exactly the paper's order: Pass 1 streams all cells to learn each feature's average; Pass 2 streams them again, subtracts that average (centers), and measures the relationships. Two laps, because centering safely needs the true average first. Runs inside gene blocks, so both explosions are tamed together. (A faster one-pass shortcut exists via --one-pass; less precise at extreme cell counts.)

The two trick-files · in words

TRICK 1 ids_batched.py

compute_IDS_blocked loops over blocks of genes. For a block against itself it calls their compute_IDS(block); for two different blocks it calls their compute_IDS(block_i, block_j), which returns exactly the cross-correlation between those two gene groups. It writes each small result into the right place in the big d × d table.

And because it only ever handles one block at a time, the sparse-to-dense conversion also happens one small block at a time — that's how "handle sparse matrices" and "gene-batching" turn out to be the same piece of code.

TRICK 2 ids_streaming.py  (with Trick 1 layered in)

compute_IDS_streaming follows the paper's two-pass order. Pass 1 (_pass1_means) streams every cell slab through the authors' feature-map (transform — imported, not rewritten) and accumulates only the mean of each feature-column (optionally saved to disk via --save-means). Pass 2 (_pass2_correlate) streams the slabs again, subtracts those saved means (centers), and accumulates centered sums-of-squares (→ spreads) and centered cross-products (→ covariances), then forms the correlation and reduces to IDS.

Learning the true average before subtracting it is the numerically robust order — the reason the paper does two passes. A faster single-pass shortcut (raw Σx·Σx²·Σxy combined at the end) is still available with two_pass=False / --one-pass. It does all this within gene blocks, so both explosions are controlled at once.

The paper's recipe · decoded line by line

The supplementary section reads as dense math. Here is each phrase in plain words, and exactly where it lives in our code. k = 6 features per gene · n = cells · d = genes · d′ = genes per block · n′ = cells per slab.

What the paper saysWhat it meansWhere it is in our code
"m files, each containing a matrix Xᵢ of size n × d" The data is too big for one piece, so it arrives in chunks. We hold one matrix and feed it in cell slabs instead of separate files — same idea, different packaging. _iter_cell_batches() in ids_streaming.py.
"center the feature-mapped variables by subtracting the mean … compute a running mean … batching over n (n′≪n) and d (d′≪d)" A correlation needs each feature's average; build it up a batch at a time instead of loading everything. This is our Pass 1 — _pass1_means() streams the cells and accumulates Σx, giving mean = Σx ⁄ n for every feature. Can be written to disk with --save-means, exactly as the paper says.
"to avoid storing an n × kd feature-mapped matrix and the kd × kd correlation matrix, we batch over the number of variables d … generate a feature-mapped n × kd′ matrix" Don't expand or correlate all genes at once — do a small block of genes at a time. (This is Trick 1.) The gene-block loop in compute_IDS_blocked() (ids_batched.py) and in compute_IDS_streaming() (ids_streaming.py).
"reshape to a tensor of size k × d′ × k × d′ … reduce to a d′ × d′ block by computing the ℓₚ-norm over the first and third dimensions" Each gene pair has a 6×6 patch of feature-correlations; collapse each patch to one number — that's the IDS score (max, mean, or L2). Done inside the authors' compute_IDS on the blocked path; replicated exactly in _reduce() in ids_streaming.py.
"normalize the kd′ × kd′ covariance matrix by the standard deviations … pre-compute these standard deviations" Correlation = covariance ÷ (spread × spread). You also need each feature's spread, measured around the mean from Pass 1. This is our Pass 2 — _pass2_correlate() subtracts the Pass-1 means, then accumulates centered Cxx (spreads) and Cxy (covariances); the divide is the Cxy / denom line.
"feasible to compute IDS using O(k²d′² + nd + nkd′) memory … far smaller than O(nkd + k²d²)" Naïve pays for the whole expanded grid + whole correlation. Batched pays only for one small block's correlation + one slab of features + the raw data. Both tricks hit this bound: peak memory is one gene block's tally (k²d′²), never the full 120k×120k.
What we deliberately did NOT copy: the paper's last paragraph — storing data as uint16 sparse HDF5, loading to GPU then float32, in-place ops, and TensorFloat32 matrix multiply — is pure speed/storage tuning, not part of the correctness logic. We keep data sparse in memory (scipy) and compute in plain float64 NumPy; only the Direct path taps their GPU/PyTorch backend, and only if torch is installed. These are optimizations to add later if the scale ever demands them — they change the speed, not the answer.

Design rule: the engine's math (ids/, the authors' compute_IDS / transform) is never rewritten. Our files only decide how to feed it — whole, in gene blocks, or in gene blocks + cell slabs. The test_*.py files prove all three routes match a single engine call to ~14 decimal places. Pick the smallest path that fits: Direct → Trick 1 → Trick 2.
